# Testing

`vitest.config.ts` runs in the node environment with forks and no file parallelism, because tests share SQLite. It picks up `backend/src/**/*.test.ts` and `frontend/src/**/*.test.ts`.

There is no DOM test environment, so frontend tests are limited to pure `.ts` modules such as `mapHelpers.test.ts`. Backend route tests build the app with `createApp` and an injected fake `weatherClient`.

**Browser checks (on demand).** UI flows that unit tests can't reach are checked in a real browser, outside `npm test` and the pre-commit hook. They add to the vitest unit tests and don't replace them.
- `scripts/e2e/town-search.sh [us1|us2|us3|themes|a11y]` drives the add form with agent-browser.
- `scripts/e2e/lightning-markers.sh [us1|us2|themes]` checks the lightning bolt markers (shape, sizes by age, popup, toggle, pins above, colour per theme). It stubs `POST /api/lightning/refresh` and `GET /api/locations` with `agent-browser network route`, so it never calls data.gov.sg.
- `scripts/e2e/lightning-grouping.sh [us1|us2]` checks lightning at storm volume (spec 009). It replays the real 37,242-strike capture from `backend/fixtures/`. 6 MB is too much for `agent-browser network route --body` (argv size), so it registers an init script that replaces `fetch` for `POST /api/lightning/refresh` only and records long tasks from before the first navigation. US1 fails on any main-thread task over 200 ms (turning lightning on, a 30 s tick, fullscreen open and close, pan, zoom, toggle), more than 1,500 marks, any mark on the card map under fullscreen, or a JS heap over 100 MB. US2 checks group count and age labels, card group → fullscreen, drilling down to a bolt popup, and all six themes. The 4× CPU phone check and the timing-record comparison use the chrome-devtools MCP (`specs/009-lightning-strike-grouping/quickstart.md` §5).
- `scripts/e2e/rain-view.sh [us1|us2|us3|us4|us5|themes]` checks the island-wide rain view (spec 011). It stubs `POST /api/rain/refresh` (12 stations: dry, every level, one partial, two missing) and `GET /api/locations` with `agent-browser network route`, so it never calls data.gov.sg. `route` cannot set a status, so failures are simulated with `--abort` (the same "unavailable" path as a 502, which `routes/rain.test.ts` covers), with the browser's "Failed to load resource" line allowed for those steps only; stubs set `fetched_at` 3 minutes back so the client's 2-minute reuse never skips a refresh. US4 counts rain requests with the Resource Timing API (none on load, none on reload with rain remembered on, none when opening full screen). `themes` checks all six themes at 375 px: the `--rain-outline` against the theme's nominal basemap colour (3:1) and the strip text (4.5:1). Since spec 011 the card's lightning switch sits in the Layers menu; `lightning-markers.sh` and `lightning-grouping.sh` open it through `toggle_card_lightning`.
- `scripts/e2e/uv-trend.sh [us1|us2|us3|themes]` checks the UV tile's hourly view (spec 008): each state (today, previous day, empty, pre-feature, unavailable) at desktop and 360 px, the Rainfall | UV / Air Quality grid, the text-only fallback at 320 px, and the bars in all six themes. It stubs `GET /api/locations` with `agent-browser network route`, so it never calls data.gov.sg.
- `scripts/e2e/use-my-location.sh [us1|us2|us3|us4|themes]` drives the "Use my location" button. It grants geolocation through CDP; where the agent-browser profile ignores that grant, it switches to a stub of `navigator.geolocation` (and says so), and the browser's own prompt is checked by hand (`specs/003-use-my-location/quickstart.md` §4).
- `scripts/e2e/privacy-notice.sh [us1|us2|themes|off]` checks the visitor-counting privacy notice (spec 012). It starts its server with `E2E_WEB_ANALYTICS=notice-only`, so the notice shows but Vercel's script never loads, and every sub-check asserts zero requests to `/_vercel/insights/` or `va.vercel-scripts.com`. It covers the empty state and the selected-location footer (click, Enter, Space, Escape, `aria-expanded`), 375 px (one line, clear of the dock, scrolls into view when opened, nothing above it moves), 4.5:1 text in all six themes (against the nearest opaque colour or every stop of a background gradient), and a second server with `off` (no notice, no meta). It stubs `GET /api/locations`.
- Web analytics is off for every other check and for vitest: `lib.sh` and `vitest.config.ts` blank `WEB_ANALYTICS` and `VERCEL`.
- chrome-devtools (MCPorter) covers the raw network log, performance traces and Lighthouse.
- The scripts share `scripts/e2e/lib.sh`. By default they start a temporary production-mode server (built `frontend/dist`, free port, throwaway database) and tear it down, with every browser session, from an `EXIT` trap on pass or fail. Run `npm run verify` first so the build is current. `E2E_BASE_URL=<url>` uses a server you run instead; `E2E_DATABASE_PATH=<file>` keeps the database between runs. The temporary server always starts with `TURSO_*` blanked, so it never touches the hosted Turso database even when `.env` points at it. vitest blanks the same variables in `vitest.config.ts`, and `resolveDatabaseConfig` refuses a hosted database when `NODE_ENV=test`.
- Error buffers are cleared before the first navigation. Any uncaught page error or `console.error` while opening or switching views fails the run at once (`assert_clean`). `E2E_ALLOW_ERRORS=<regex>` ignores known messages.
- Output goes to the git-ignored `e2e-artifacts/`.

**Verification gate.** `npm run verify` runs lint -> typecheck -> tests -> build and stops at the first failure. It adds to the pre-commit hook (`npm run lint`, `npm test`), which is unchanged. While Claude Code edits, a per-file `PostToolUse` hook (`.claude/hooks/post-edit-lint.sh`) runs Prettier and `eslint --fix` on the edited file.
