# Architecture

**One process serves both halves.** `backend/src/server.ts` builds the Express app (`createApp`) and, outside tests, mounts Vite as middleware in dev or serves `frontend/dist` in production. `scripts/dev.mjs` wraps `tsx watch backend/src/server.ts` in Portless, which picks a random port and gives the stable `.localhost` URL. The frontend only calls relative `/api/*`, so there is no CORS or port configuration. `createApp` takes a `weatherClient` option so tests inject a fake provider instead of calling data.gov.sg.

**Per-visitor lists (spec 013).** Every saved place belongs to one anonymous visitor. The browser makes a random 43-character key (32 bytes, base64url, `frontend/src/visitorKey.ts`), keeps it in `localStorage` under `weather-starter.visitor.key` (in memory for the page if storage is blocked), and `api.ts` sends it only as the `X-Visitor-Key` header on `/api/locations*`. The header is never put in a URL, logged (request logs keep no headers) or sent with interaction logs or analytics. There's no cookie, so the privacy notice's "no cookies" stays true. A cross-site page can't attach a custom header without a CORS preflight, which this same-origin app never answers, so no other site can act with a visitor's key. `backend/src/visitors.ts` checks the format (`visitorKeyFormat.ts`, db-free) and looks the visitor up by SHA-256 (`visitors.key_hash`); the plaintext key is never stored. Every query in `db.ts` takes a `visitorId`:
- A list with no key, a malformed key or an unknown key is empty (200).
- Another visitor's place answers `404 Location not found`, the same as a missing id, and costs no weather call.
- Creating needs a valid key (400 `A visitor key is required`, after the 422 body checks) and makes the visitor on first save.
- Duplicate coordinates are refused per visitor (unique index `visitor_id, latitude, longitude`), so two visitors may save the same place.
- A known key's use bumps `visitors.last_used_at` at most once an hour.
- A retention sweep (startup, then at most every 6 hours, in the background) deletes visitors unused for 90 days with their places.
- Rows from before spec 013 have `visitor_id` NULL. They're hidden from everyone and never swept until the owner runs `npx tsx backend/src/claimLegacyCli.ts "$KEY" --remote` (`backend/src/claimLegacy.ts`). The CLI doesn't load `.env` and refuses Turso without `--remote`; see [deployment.md](deployment.md).

**Snapshot pattern.** The app never calls data.gov.sg per page load. Creating a location stores coordinates, then immediately refreshes it; `GET /api/locations` only reads SQLite; `POST /api/locations/:id/refresh` re-fetches and overwrites the stored snapshot. `backend/src/weather.ts` (`SingaporeWeatherClient`) merges several data.gov.sg endpoints (2-hour, 24-hour and 4-day forecasts, station readings, air quality) into one `WeatherSnapshot`, matching the nearest forecast area, region or station by coordinates. From the same `psi` response it also stores the region's pollutant concentrations (PM10, O3, NO2, SO2, CO) and `air_quality_observed_at`, so the breakdown adds no upstream call. It also stores NEA's heat-stress reading from `weather?api=wbgt`: the WBGT value, level, station name, reading time and the great-circle distance (km) to the nearest station with a numeric reading, kept even when that station is far. From the same `uv` response it stores `uv_hourly` (spec 008): the record's hourly list oldest first, with the record's own `date` and `as_of` (the provider's `updatedTimestamp`). Overnight, from about 19:11 to 07:11, the provider keeps returning the previous day's full list, so `date` is that day; a missing `date` falls back to the oldest reading's Singapore day, then the record timestamp's. `uv_hourly` is null only for pre-feature rows, a failed `uv` call, or a record with no readable day. It adds no upstream call (12 calls per refresh, pinned by a test in `weather.test.ts`). `forecast_periods` keeps every 24-hour period in NEA's order, including one without wording (`forecast: ''`) or without a label, because the frontend times periods by position (spec 018). It is empty only when no period has wording. Unrefreshed locations carry a default snapshot (`condition: 'Not refreshed'`, null readings), which the UI renders as `--°`.

**Lightning exception.** Island-wide lightning strikes were the first weather call outside a location create/refresh (constitution Principle I, 1.1.0; rain joined in 1.5.0, below). `POST /api/lightning/refresh` (`backend/src/routes/lightning.ts`) is called only on a user action, never on page load. `SingaporeLightningClient` (`backend/src/lightning.ts`) reads data.gov.sg's `weather?api=lightning` dataset (paging back 60 minutes), normalises strikes, and caches one window in memory for 2 minutes shared by all callers; if a refresh fails it serves the previous window with `stale: true`, else the route returns 502. Nothing is stored in SQLite or in any `WeatherSnapshot`. Valid strikes anywhere in the region are kept (the feed covers more than the island). It is injected like the weather client (`createApp({ lightningClient })`); `LIGHTNING_FIXTURE=demo` (development only) serves three fake strikes aged 2, 30 and 55 minutes, `LIGHTNING_FIXTURE=busy` about 370 deterministic strikes across the region and the hour (a busy normal day), and `LIGHTNING_FIXTURE=storm` a replay of the real 2026-11-16 storm (37,242 strikes, `backend/fixtures/lightning-storm-2026-11-16.json.gz`, times moved to now) for checking storm-scale behaviour. All three are ignored in production. Responses are compressed (`compression` middleware in `createApp`: brotli or gzip when the browser accepts it), which takes the storm window from about 6.2 MB to about 0.55 MB on the wire; the JSON body is unchanged. Shared HTTP behaviour lives in `backend/src/providerHttp.ts`. The provider's rate limit is per key, so `createApp` builds one `ProviderRequester` and passes it to every default client (locations, lightning and rain), which keeps every call in one paced stream. Lightning and rain request with `priority: 'high'`, so their one to four calls take the next free slot ahead of a location refresh's queued calls instead of waiting about 10 s behind them (spec 011, T057); the spacing between calls is unchanged. Request starts are spaced `ceil(10000 / limit) + 50` ms apart: 884 ms with a key (Development tier, 12 per 10 s), 1717 ms without one (6 per 10 s), or the value implied by an optional `WEATHER_API_RATE_LIMIT` (requests per 10 s, e.g. 30 for a Production key). A 429 is retried once after 10 s. A refresh therefore takes about 10 s with the Development key when a 429 forces the retry; without one it is about 1 s (measured 2026-11-15 with a key: 2 pages, 743 ms of it pacing). **Refresh timing (diagnostics only).** `ProviderRequester.getJson(url, stats?)` adds requests, pacing wait and 429 retries to an optional `RequestStats`. `SingaporeLightningClient` fills a `LightningTiming` per call (served from `cache`, `shared` with a load in flight, or `fetch`; pages, requests, pacing, retries, provider time, strike count, outcome and a fixed `errorKind`) and logs it once as `lightning refresh timing`. The route sends the same numbers as a standard `Server-Timing` header (`backend/src/serverTiming.ts`) on 200 and 502. Only numbers and fixed enums are written, never URLs, keys or provider text. Client tests pass `requestIntervalMs: 0` and `rateLimitRetryDelayMs: 0`.

**Rain exception.** Island-wide rain (spec 011, constitution Principle I, 1.5.0) uses the same terms. `POST /api/rain/refresh` (`backend/src/routes/rain.ts`) is called only on a user action, never on page load; the layer is off by default. `SingaporeRainClient` (`backend/src/rain.ts`) makes one `rainfall?date=<today SGT>` request (first page only: the newest 25 five-minute readings, newest first), plus one for the previous SGT date when the window reaches before midnight or today has no data yet. The newest period fills in over several minutes, so the anchor is the newest period holding at least 80% of the largest row count (normally about 10 minutes old); each station's total is the sum of the three five-minute periods ending there, with `periods_covered` 0–3 and `total_mm: null` when it has none. One observation is cached in memory for 2 minutes and shared by all callers (concurrent callers share one load); a failed refresh serves the previous one with `stale: true`, else the route returns 502 `Rain data is currently unavailable`. Nothing is stored in SQLite or in any `WeatherSnapshot`. It shares the paced `ProviderRequester` and needs no per-device limit, because the shared cache caps upstream at one rain fetch per 2 minutes and a failed attempt is also remembered for 2 minutes. It is injected with `createApp({ rainClient })`; `RAIN_FIXTURE=demo` (development only, ignored in production) serves 20 hand-made stations. Timing is logged as `rain refresh timing` and sent as `Server-Timing` (`formatServerTiming` takes any timing with the shared cost fields). On the frontend, the store's `rain` slice mirrors lightning's (in-flight guard, 2-minute reuse, earlier readings kept on failure), the card map holds both layers' switches in one Layers menu with one combined strip (`MapLayersControl.tsx`), and the full-screen map stacks the rain strip above lightning's.

**Temperature and wind exception.** Island-wide air temperature and wind (spec 015, constitution Principle I, 1.6.0) use the same terms. `POST /api/temp-wind/refresh` (`backend/src/routes/tempWind.ts`) is called only on a user action, never on page load; the view is off by default and appears on the **full-screen map only** (the card map at focus zoom shows about one station). `SingaporeTempWindClient` (`backend/src/tempWind.ts`) makes three "latest" requests, `air-temperature`, `wind-speed` and `wind-direction` (no `date`, so each returns the newest complete minute), at `priority: 'high'`, and joins them by station id. Each measure succeeds or fails on its own: if temperature fails the wind still shows, and vice versa (`measures.temperature` / `measures.wind` = `'unavailable'`); wind needs both the speed and the direction response. A failed measure is never filled from an older observation, so the view never mixes ages. Values outside 10–45 °C, 0–150 knots or 0–360° read as "no reading". One observation is cached for 2 minutes and shared; when all three calls fail it serves the previous one with `stale: true`, else the route returns 502 `Temperature and wind data is currently unavailable`. Nothing is stored in SQLite or in any `WeatherSnapshot`. It is injected with `createApp({ tempWindClient })`; `TEMP_WIND_FIXTURE=demo` (development only) serves about 17 hand-made stations covering every state. On the frontend the store's `tempWind` slice mirrors rain's; `WeatherMap`'s `showTempWind` prop defaults to `false` and only `MapFullscreen` passes `true`. Its strip sits between rain's and lightning's, readings count as out of date after 15 minutes (the provider normally lags 3–7 minutes), and its marks sit in a pane between rain and lightning.

**Storage.** `backend/src/db.ts` uses Drizzle's `sqlite-proxy` driver and runs migrations from `backend/drizzle/` at import time (top-level await). The schema is `backend/src/schema.ts`. Underneath, an adapter (`backend/src/dbAdapter.ts`) chooses the store:
- **Local:** Node's built-in `node:sqlite` (`DatabaseSync`, WAL). The path defaults to `backend/weather.db` and can be overridden with `DATABASE_PATH`.
- **Turso:** the hosted libSQL database through `@libsql/client/web` (pure JS over HTTP). Used when `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` are both set.

`resolveDatabaseConfig` (`backend/src/dbConfig.ts`) refuses to start when:
- only one Turso variable is set;
- `DATABASE_REQUIRE_REMOTE=true` (set in the container image) has no Turso;
- `NODE_ENV=test` would select Turso.

vitest and the e2e server also blank `TURSO_*`. Both stores share the same migrator, so the `__drizzle_migrations` history is read the same way in each. Startup logs `database ready` with `{ kind, migrationsApplied }`, never the URL or token. If the database cannot be opened or migrated, startup logs the cause and exits non-zero without deleting or recreating anything.

The server listens on `HOST` (default `127.0.0.1`) and `PORT` (default `3000`). On `SIGTERM` it stops taking requests, closes the database and exits, with a 25 s limit. Hosting, CI/CD and secrets are described in [deployment.md](deployment.md). Creating a location is durable and non-fatal on refresh problems: the row is inserted first, a concurrent duplicate (unique index) returns 409, and any weather failure on the first refresh still returns 201 with the default snapshot.

**Frontend.** React 18 + Tailwind 3, no router. All server state lives in one context, `frontend/src/state/store.tsx` (locations, selected id, add/delete/refresh with per-id refreshing state), backed by `frontend/src/api.ts`. `Layout` = `Sidebar` (location cards, add form) + `Hero` (selected location: hourly strip, 10-day forecast, map card, tile grid). `Hero` returns early when nothing is selected, so the map card only shows with a selected location. A failed load keeps the list already on screen and shows `loadError` with a Retry button in `Sidebar`. Frontend interactions are reported to `POST /api/logs`. Visitor counting (spec 012) is decided once by the server: `backend/src/analyticsMode.ts` turns `WEB_ANALYTICS` (falling back to `VERCEL=1`) into `measure`, `notice-only` or `off`, and `renderIndexHtml` writes it into `<meta name="web-analytics">`. `App` renders Vercel's `<Analytics mode="production">` only for `measure`, with `beforeSend` stripping the query and fragment, and `Hero` shows `PrivacyNotice` in its footer and empty state unless the mode is `off`. The Vite dev server never writes the meta, so local runs count nothing. Page-speed measurement (spec 016) follows the same pattern with its own setting, `SPEED_INSIGHTS`: `renderIndexHtml` writes `<meta name="speed-insights">`, and in `measure` mode the server pre-renders two pages that differ only in `<meta name="speed-insights-visit" content="cold|warm">`, picking one per request with `pageFor` (`backend/src/speedInsights.ts`: `cold` when the instance is under 10 s old). `App` renders `<SpeedInsights route="/cold|/warm">` only for `measure`, and `Hero` builds the notice's words with `analytics/privacyCopy.ts`, which names only what is active. The add form has a town search: `components/towns.ts` is a static copy of the 47 NEA two-hour forecast areas (captured 2026-11-14), and `components/townSearch.ts` matches typed text against it. Matching ignores case and spaces, matches word starts, allows one wrong letter for 3+ characters, and returns at most 8 results. Picking a town only fills the latitude and longitude, and the user still presses Add. Searching makes no network call. A location at an area's own point is labelled with that area by the existing nearest-area match. A "Use my location" button sits beside Add Location (`components/UseMyLocation.tsx`). Each press makes one `navigator.geolocation.getCurrentPosition` request through `components/geolocation.ts`; there is no tracking and nothing runs on page load. The pure `components/geolocate.ts` then decides: outside the server's Singapore box (checked on the client first, so no request is sent), within 100 m of a saved place (`savedNear`, which selects that place instead of adding), or a new place added through the normal `create`. Creates from this source call `create(payload, { source: 'geolocation' })`, so their interaction logs carry the source, outcome and area but never the coordinates. Two tiles are derived on the client and never stored: "Feels like" (`components/feelsLike.ts`, Steadman apparent temperature from stored temperature, humidity and wind, with comfort bands, clothing advice and an umbrella note) and sunrise/sunset (`components/sunTimes.ts`, NOAA approximation from the location's coordinates and today's Singapore date, re-checked by a 60-second `useNow` tick). The "Heat Stress" tile (`components/heatStress.ts`) reads the stored WBGT fields and applies the 10 km cut-off on the client: no reading gives "No reading", a nearest station more than 10 km away gives "No nearby station", and NEA-advisory guidance appears only at Moderate or High. All three are pure modules with unit tests and make no weather calls. The UV tile spans two grid columns and shows the snapshot day's hourly readings: `components/uvTrend.ts` (pure, unit-tested) gives the UV bands, 13 slots from 07:00 to 19:00, Rising/Steady/Falling from the last two readings (today only), the count of hours at UV 3+, NEA's 11 am – 3 pm peak window, the NEA/HealthHub guidance wording and the five tile states (readings, previous day, empty, pre-feature, unavailable). "Today" is the Singapore date of the `useNow` tick, so an overnight snapshot is labelled with its own date. The outdoor grid is Rainfall | UV (two columns each), then Air Quality across the row. Their "No reading" state is new; older tiles still show `--` for missing values.

**Forecast timing (spec 018).** The stored forecasts say when they apply only in words, and NEA's printed dates are often wrong. `components/forecastTiming.ts` (pure, unit-tested) reads just the clock words and places them with the snapshot's reading time, in fixed UTC+8:
- The first period and the 2-hour window start at the latest such clock time no later than the reading time + 2 hours. Each later period starts where the previous one ends.
- An unreadable label, a break in that chain or a missing reading time leaves the time unknown. It is never guessed, and never "now".
- `forecastOutlook(weather, now)` marks each forecast ended, active, upcoming or unknown. A window includes its start and excludes its end. A stale reading (3 hours) is judged at its reading time.
- The top line (`outdoorSummary.ts`), the strip's labels (`stripLabels`) and the sky (`theme/sky.ts`) all use that outlook and `Layout`'s one 60-second clock, which `Layout` passes to `Hero`. They change together and fetch nothing.
- Forecast rain is named before any thunder part, always as a forecast. The first that applies wins: the 2-hour forecast ("Showers forecast now", or "Showers forecast" when untimed), period rain in force ("… until <time>"), rain starting before any thunder ("… from <time>"), then untimed period rain. "Until" closes the unbroken run of rain periods, called "Rain" if their wordings differ, and is left out when the period after the run has no wording or no known time.
- In the top line, thunder in force stands alone as "Thundery showers now". Untimed 2-hour thunder ("Thundery showers forecast") outranks later thunder ("from <time>"), because it may already apply. "No storms forecast" needs a timed period still to run, no rain or thunder that may still apply, no such period without wording, and no rain or thunder in the 2-hour condition, even an ended one.

**Installable app (spec 014).** The app installs as "Lepak". `frontend/public/` (copied as is into `frontend/dist/` by Vite and served by the existing `express.static`) holds `manifest.webmanifest` (name and short name "Lepak", `display: standalone`, `theme_color` and `background_color` `#202a36`, 192, 512 and maskable 512 PNG icons), `favicon.svg`, `icons/` (rendered once from `frontend/icons/lepak-mark.svg` by `scripts/icons/render-icons.sh` and committed), `offline.html` and `sw.js`. `index.html` adds the manifest link, `theme-color`, the Apple touch icon and the `apple-mobile-web-app-*` tags; the page title stays "Weather". **Offline helper**: `sw.js` caches exactly one file, `/offline.html` (self-contained: inline styles and artwork, no visitor data), in `lepak-offline-<hash>`, named after the first 8 hex digits of the SHA-256 of `offline.html` (`frontend/src/install/offlineCacheName.test.ts` fails when the two drift, so editing the page always updates the worker). It acts only on same-origin page navigations, with navigation preload on where supported: it passes them to the network and, only if that fetch rejects (no connection), answers with the offline page. Any HTTP response, error statuses included, passes through, and every other request (`/api`, scripts, styles, tiles, fonts, analytics) is never intercepted. The app's own files are never cached, so a deploy or rollback reaches users on their next online visit. `frontend/src/install/offlineHelper.ts` registers it after `load` in production builds only (`updateViaCache: 'none'`); building with `VITE_OFFLINE_HELPER=off` unregisters it instead, and `scripts/pwa/sw-kill.js` is the matching switch-off worker (see `docs/deployment.md`). `backend/src/staticHeaders.ts` serves `/sw.js` and the manifest with `Cache-Control: no-cache`. A first visit while offline still gets the browser's own error page. **iPhone/iPad Add to Home Screen button**: iOS Safari has no install prompt, and a home-screen app gets its own storage, separate from Safari's, so it starts with a new visitor key and an empty list. After the first saved place, iPhone/iPad Safari (not other iOS browsers or in-app browsers, and not when already installed) shows an "Add Lepak to Home Screen" button on its own line directly under Use my location and Add Location (`components/InstallHint.tsx`, rendered in `Sidebar`'s button row, so phones see it too). It carries a dot until first opened, and opens a non-modal tip with the steps and the separate-list warning. Escape or a tap outside closes the tip; **Got it** removes the button for good. The pure `install/installHint.ts` (unit-tested) decides from the user agent, touch points, standalone mode, the saved count and two `localStorage` flags, `weather-starter.install-hint.seen` and `weather-starter.install-hint.dismissed`, which never leave the device. Nothing about install or home-screen use is measured.

**Map.** `frontend/src/components/map/` (Leaflet via react-leaflet): `LazyMapCard` (code-splits the map: Leaflet loads only when the card comes within 600px of view, behind a same-size placeholder), `MapCard`, `MapFullscreen` (portal overlay), `WeatherMap`, and pure helpers in `mapHelpers.ts`. Pins come from the data `GET /api/locations` already returns, so the map makes no weather calls. Tiles are CARTO; `VITE_CARTO_API_KEY` in `frontend/.env.local` is optional (falls back to keyless tiles). The basemap style comes from the active theme.

**Lightning layer.** Strikes that crowd together at the current zoom are drawn as one group mark; the rest are single bolts (spec 009). One marker per strike froze the page in storms (15 s at 37,242 strikes) because Leaflet's cost of adding markers grows with the square of their number, so the layer draws only what the view needs. `lightningGroups.ts` (pure, unit-tested) indexes the strikes in the window with `supercluster` (40 px radius, groups form up to zoom 20) and turns the view (bounds padded 25 %, zoom) into marks: a group with its count, newest-strike age step and "Nm" label, or a single bolt. `LightningLayer` keeps those marks in one Leaflet layer group in its own pane (below the pins, so pins stay clickable) and diffs them on every pan, zoom, new observation and 30-second tick, adding, removing or re-iconing only what changed; the index is rebuilt only when the strikes in the window change. That keeps the marks to a few hundred (about 500 on the card and 1,100 in fullscreen at storm volume). Bolts keep the spec 007 look (`strikeMarker.ts`, 12 cached age icons); group marks come from `groupMarker.ts` and are coloured by `--lightning`, `--lightning-outline` and `--lightning-ink` in CSS (see `docs/theming.md`). Popups are built on click with DOM text, never HTML from strike data. Selecting a group zooms to where it splits; in the card map it opens fullscreen there instead (`onLightningGroupSelect`); a group that can't split at the deepest zoom lists its 20 newest strikes. While fullscreen is open the card map's layer is empty (`showLightning={false}`), so nothing is drawn twice. The marks are not Tab stops; the status strip gives the count ("37,242 strikes in the last hour"). After each refresh the browser console gets one `[lightning] refresh timing` record (`lightningTiming.ts`): network time, drawing time (measured by the layer from applying the observation to the second animation frame after, so it covers the marker work; within 2 % of a DevTools trace), group and bolt counts, the parsed `Server-Timing` and, when the 2-minute check skipped the request, `served: "reused"`; `LightningControl.tsx` provides the on/off switch (a native `role=switch` button) and refresh button (`LightningButtons`) and the status strip (`LightningStatusStrip`: idle prompt, loading, empty, unavailable, count + last-updated time); the full-screen map places them beside rain's, and the card holds them in its Layers menu (spec 011). State lives in the `lightning` slice of `store.tsx`: the on/off choice is saved in `localStorage` (`weather-starter.lightning.enabled`, default on), data is requested only by turning the layer on or pressing refresh/the idle prompt, and data under 2 minutes old is reused. Strikes keep fading and expire on a 30-second client tick with no network call. Pure logic (age styling, status text, freshness, popup text) is in `lightningHelpers.ts` and unit-tested.
