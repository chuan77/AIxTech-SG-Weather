# Architecture

**One process serves both halves.** `backend/src/server.ts` builds the Express app (`createApp`) and, outside tests, mounts Vite as middleware in dev or serves `frontend/dist` in production. `scripts/dev.mjs` wraps `tsx watch backend/src/server.ts` in Portless, which picks a random port and gives the stable `.localhost` URL. The frontend only calls relative `/api/*`, so there is no CORS or port configuration. `createApp` takes a `weatherClient` option so tests inject a fake provider instead of calling data.gov.sg.

**Snapshot pattern.** The app never calls data.gov.sg per page load. Creating a location stores coordinates, then immediately refreshes it; `GET /api/locations` only reads SQLite; `POST /api/locations/:id/refresh` re-fetches and overwrites the stored snapshot. `backend/src/weather.ts` (`SingaporeWeatherClient`) merges several data.gov.sg endpoints (2-hour, 24-hour and 4-day forecasts, station readings, air quality) into one `WeatherSnapshot`, matching the nearest forecast area, region or station by coordinates. From the same `psi` response it also stores the region's pollutant concentrations (PM10, O3, NO2, SO2, CO) and `air_quality_observed_at`, so the breakdown adds no upstream call. It also stores NEA's heat-stress reading from `weather?api=wbgt`: the WBGT value, level, station name, reading time and the great-circle distance (km) to the nearest station with a numeric reading, kept even when that station is far (12 calls per refresh). Unrefreshed locations carry a default snapshot (`condition: 'Not refreshed'`, null readings), which the UI renders as `--°`.

**Lightning exception.** Island-wide lightning strikes are the one weather call outside a location create/refresh (constitution Principle I, 1.1.0). `POST /api/lightning/refresh` (`backend/src/routes/lightning.ts`) is called only on a user action, never on page load. `SingaporeLightningClient` (`backend/src/lightning.ts`) reads data.gov.sg's `weather?api=lightning` dataset (paging back 60 minutes), normalises strikes, and caches one window in memory for 2 minutes shared by all callers; if a refresh fails it serves the previous window with `stale: true`, else the route returns 502. Nothing is stored in SQLite or in any `WeatherSnapshot`. Valid strikes anywhere in the region are kept (the feed covers more than the island). It is injected like the weather client (`createApp({ lightningClient })`); `LIGHTNING_FIXTURE=demo` (development only) serves three fake strikes aged 2, 30 and 55 minutes. Shared HTTP behaviour lives in `backend/src/providerHttp.ts`. The provider's rate limit is per key, so `createApp` builds one `ProviderRequester` and passes it to both default clients, which keeps every call in one paced stream. Request starts are spaced `ceil(10000 / limit) + 50` ms apart: 884 ms with a key (Development tier, 12 per 10 s), 1717 ms without one (6 per 10 s), or the value implied by an optional `WEATHER_API_RATE_LIMIT` (requests per 10 s, e.g. 30 for a Production key). A 429 is retried once after 10 s. A refresh therefore takes about 10 s with the Development key. Client tests pass `requestIntervalMs: 0` and `rateLimitRetryDelayMs: 0`.

**Storage.** `backend/src/db.ts` uses Node's built-in `node:sqlite` (`DatabaseSync`) behind Drizzle's `sqlite-proxy` driver, and runs migrations from `backend/drizzle/` at import time (top-level await). The schema is `backend/src/schema.ts`. The DB path defaults to `backend/weather.db` and can be overridden with `DATABASE_PATH`. If the database cannot be opened or migrated, startup logs the cause and exits non-zero without deleting or recreating the file. Creating a location is durable and non-fatal on refresh problems: the row is inserted first, a concurrent duplicate (unique index) returns 409, and any weather failure on the first refresh still returns 201 with the default snapshot.

**Frontend.** React 18 + Tailwind 3, no router. All server state lives in one context, `frontend/src/state/store.tsx` (locations, selected id, add/delete/refresh with per-id refreshing state), backed by `frontend/src/api.ts`. `Layout` = `Sidebar` (location cards, add form) + `Hero` (selected location: hourly strip, 10-day forecast, map card, tile grid). `Hero` returns early when nothing is selected, so the map card only shows with a selected location. A failed load keeps the list already on screen and shows `loadError` with a Retry button in `Sidebar`. Frontend interactions are reported to `POST /api/logs`. The add form has a town search: `components/towns.ts` is a static copy of the 47 NEA two-hour forecast areas (captured 2026-11-14), and `components/townSearch.ts` matches typed text against it. Matching ignores case and spaces, matches word starts, allows one wrong letter for 3+ characters, and returns at most 8 results. Picking a town only fills the latitude and longitude, and the user still presses Add. Searching makes no network call. A location at an area's own point is labelled with that area by the existing nearest-area match. Two tiles are derived on the client and never stored: "Feels like" (`components/feelsLike.ts`, Steadman apparent temperature from stored temperature, humidity and wind, with comfort bands, clothing advice and an umbrella note) and sunrise/sunset (`components/sunTimes.ts`, NOAA approximation from the location's coordinates and today's Singapore date, re-checked by a 60-second `useNow` tick). The "Heat Stress" tile (`components/heatStress.ts`) reads the stored WBGT fields and applies the 10 km cut-off on the client: no reading gives "No reading", a nearest station more than 10 km away gives "No nearby station", and NEA-advisory guidance appears only at Moderate or High. All three are pure modules with unit tests and make no weather calls. Their "No reading" state is new; older tiles still show `--` for missing values.

**Map.** `frontend/src/components/map/` (Leaflet via react-leaflet): `MapCard`, `MapFullscreen` (portal overlay), `WeatherMap`, and pure helpers in `mapHelpers.ts`. Pins come from the data `GET /api/locations` already returns, so the map makes no weather calls. Tiles are CARTO; `VITE_CARTO_API_KEY` in `frontend/.env.local` is optional (falls back to keyless tiles). The basemap style comes from the active theme.

**Lightning layer.** `LightningLayer` draws one fading `CircleMarker` per strike in its own Leaflet pane (below the pins, so pins stay clickable); `LightningControl` renders the on/off switch (a native `role=switch` button), a refresh button and a status strip (idle prompt, loading, empty, unavailable, count + last-updated time). State lives in the `lightning` slice of `store.tsx`: the on/off choice is saved in `localStorage` (`weather-starter.lightning.enabled`, default on), data is requested only by turning the layer on or pressing refresh/the idle prompt, and data under 2 minutes old is reused. Strikes keep fading and expire on a 30-second client tick with no network call. Pure logic (age styling, status text, freshness, popup text) is in `lightningHelpers.ts` and unit-tested.
